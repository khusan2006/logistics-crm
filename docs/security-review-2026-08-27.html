How exposed is the CRM to attack & to a hostile employee?

A full-codebase security review of the Logistika CRM, focused on the question the customer actually asked: what can an outsider with no account, a low-privilege staff member, or a just-fired employee do to the system?

Scope  Django app · accounts, crm, config Method  Static review, 3 parallel audits + manual verification Date  27 Aug 2026 Status  Findings 1–3 fixed in code · 2 286 tests pass

Update — the code fixes for Findings 1, 2 and 3 have been applied. The hardcoded superuser password is gone from the source (it now comes from a SEED_OWNER_PASSWORD environment variable, or is randomly generated and shown once), and both export leaks now drop their sensitive columns for non-admin roles. Five new tests lock the behavior in; the full suite of 2 286 tests passes.

One action is still yours: the code fix cannot change the password already stored in the live database. Rotate the production otabek password now — until you do, the old one from the repository still works.

Bottom line: the foundation is genuinely solid, and three real issues need fixing. Every page requires login, every data-changing and money-touching action is checked against the user's role on the server (not just hidden in the UI), forms are protected against CSRF, and — importantly for your customer — deactivating an employee immediately ends their active session, not just their next login. The production database backups sitting in the project folder are not in git, so a departing employee who cloned the repo does not walk away with customer data.

The three things to fix: (1) a superuser password is written into the source code and gets installed on deploy, so anyone who ever had the code knows an admin login; (2) two Excel export buttons hand hidden financial figures to roles that are not supposed to see them; (3) a few smaller hardening gaps. None require a rewrite — they are targeted fixes.

Findings that need action

01

An admin password is written into the code and installed on deploy

High hardcoded-credential Outsider · Former employee

The deploy start command runs a seeding step (import_prototype --if-empty) that, on an empty database, creates a full Django superuser: username otabek, password otabek12345. Both values are hardcoded in crm/seeding.py:25-26 and the command even prints them to the deploy log. This account has the top ADMIN role and access to /admin — full control of payments, cash, exports, and user accounts.

Exploit scenario

Anyone who has ever had a copy of the repository — a former developer or employee who cloned it, or anyone who saw a Railway deploy log — goes to the production login page, types otabek / otabek12345, and is in as a superuser. Because the password is only set the first time the account is created, it stays valid forever unless someone manually changed it after the first deploy. And if the database is ever re-provisioned, the same known password gets re-installed silently.

Verified

Confirmed directly in crm/seeding.py, railway.json, and Procfile — this runs on every boot.

Fix

Rotate the live otabek password today. Then change the seeding to read the owner password from an environment variable (or generate a random one and print it once), remove the hardcoded value and the log echo, and refuse to create the owner in production unless that variable is set.

02

The contract Excel export gives translators every price, payment, and debt

High cross-role-data-exposure Low-privilege employee

On the Kelishuvlar (contracts) page, the money columns — price in $ and so'm, totals, paid, and outstanding debt — are hidden from the translator role in the UI. But the Excel export button is shown to translators, and the export (crm/views.py:6489, allowed to TRANSLATOR) always builds the full table including all eight money columns. The screen hides the numbers; the download hands them over.

Exploit scenario

A translator logs in, opens Kelishuvlar, clicks the Excel button, and receives a spreadsheet with every contract's prices, totals, payments, and debts — exactly the commercial figures the role is not meant to see.

Verified

Confirmed: the export calls _contracts_table, whose headers always include Narx, Jami, To'langan, and Qarz. The codebase already knows the right pattern — the shipments export passes include_customs=request.user.is_admin_role to strip sensitive columns for non-admins.

Fix

Mirror the shipments export: pass an include_money=request.user.is_admin_role flag into _contracts_table and drop the money columns for non-admins. Add a test that asserts those column headers are absent for a translator.

03

The warehouse export leaks the company's cost price (margin) to the skladchi

High cross-role-data-exposure Low-privilege employee

Same shape as the previous finding. The Ombor (warehouse) page hides landed cost price (tan narx) from the warehouse role, but the Ombor Excel export (crm/views.py:6537, allowed to SKLADCHI) always includes the four cost-price columns in both currencies.

Exploit scenario

A warehouse employee opens the Ombor page, clicks the Excel button, and reads the company's cost per brand — the figure that reveals the profit margin, deliberately withheld from that role on screen.

Verified

Confirmed in _ombor_table: headers always include the "Tan narx" columns regardless of role.

Fix

Gate the four Tan narx columns on request.user.is_admin_role, the same way the shipments export gates its customs columns.

04

Smaller hardening gaps

Low defense-in-depth
  • Password policy not enforced in the app's own user form. When an admin creates a colleague's account at /users/new/, Django's password-strength rules are skipped (they only apply in /admin). An admin could set a one-character password. accounts/forms.py:43-53 — call validate_password() in the form.
  • Excel formula injection. A translator-controlled field (transport / container) is written into the admin's Yuklar spreadsheet as-is; a value starting with = becomes a live formula when the admin opens it. crm/exports.py:66 — prefix cells starting with = + - @ with an apostrophe.
  • Re-seed guard is narrow. The "don't wipe existing data" guard on redeploy checks only whether the Partner table has rows. In the unlikely case that partners are empty while customer/payment data exists, a routine redeploy would wipe it. crm/management/commands/import_prototype.py:145 — guard on any of the wiped tables.
  • In-app account disabling. Deactivating an employee works, but is only reachable through /admin — the CRM's own user screen has no "disable account" control. Worth adding so admins don't need the Django admin to off-board someone.

Insider-threat posture — what actually happens when you fire someone

Killing access
Works Setting an employee inactive logs them out on their very next request, not just at next login. They also can't log back in. This is the behavior you want.
Role enforcement
Works All 121 CRM views carry a server-side role check; every money-changing action (payments, cash, conversions, expenses, exports) is admin-only. Hiding in the UI is backed by real server checks — a low-privilege user cannot bypass it by crafting requests, except for the two export leaks above.
Accountability
Works Destructive and financial actions are logged to an audit trail (79 recording points across creates, edits, deletes, and status changes), and the audit log itself is admin-only. If someone acts in anger, there is a record of who did what.
Repo & data
Works The production database dumps in the project folder are correctly excluded from git and were never committed. A cloned repo contains no customer data. Gap It does contain the admin password (Finding 01) — the one thing a cloned repo hands a former employee.
Admin panel
Works Django /admin is live in production but only ADMIN-role users are ever staff/superusers, and the same brute-force lockout guards its login.

This review is a static (source-code) analysis and covers the codebase as of 27 Aug 2026.
